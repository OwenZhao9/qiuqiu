# 架构文档规范

给丘丘项目用。来源是 arc42 模板（章节结构）和 BMAD-METHOD v6 的 architecture spine（决策写法与准入规则），两者都做了裁剪，只留对本项目成立的部分。

## 怎么用这份规范

现有的 `docs/ARCHITECTURE.md`、`docs/CONTRACTS.md`、`docs/CONVENTIONS.md` 不推倒重写。按下面的结构**重排和补缺**：已有内容搬到对应节，缺的节补上，规范里没列的节不要新增。

改完之后，判断这份规范是否生效的唯一标准是：**八个 Agent 各自读完自己那份任务书 + 架构文档，独立开工，产出的代码能合到一起**。合不到一起的地方，就是架构文档漏掉的地方。

---

## 一、准入测试：什么该写进架构文档

写任何一条之前，先过这个测试：

> 如果两个模块各自独立实现这一点，它们会不会选出互不兼容的方案？

三个条件同时成立才写进来——**会不兼容**，**并且**这个决定不显然，**并且**确实是个真实权衡。任一条不成立，丢进「已推迟」那一节，写清为什么可以等。

反例，都不该写进架构文档：

- 「用 TypeScript 写前端」——已经在技术栈表里，不是决策
- 「函数要写注释」——是代码规范，不是架构约束
- 「LanceDB 比 Chroma 快」——是理由，不是决策（见第三节）

正例：

- 「状态机切换不经过后端」——前端和后端各自实现会选出不兼容的方案，且是延迟与一致性的真实权衡
- 「主动输入跳过筛选」——输入层和记忆中间件对「什么算噪音」的理解不一致就会打架

## 二、文档结构：八节

砍掉了 arc42 的部署视图（单机应用没有部署拓扑）、术语表（单人项目）、风险与技术债（等跑起来再建）。剩八节，顺序固定。

| # | 节名 | 该写什么 | 硬规则 |
|---|---|---|---|
| 1 | 目标与质量属性 | 这个系统要做成什么样，质量属性**排序** | 必须排序，不能并列。「首字延迟 > 记忆准确率 > 成本」这样写 |
| 2 | 约束 | 授权、平台、成本、隐私。不可协商的外部条件 | 每条注明约束来源（许可证 / 平台限制 / 自己定的），来源不同处理方式不同 |
| 3 | 系统边界 | 什么在系统内、什么在外。所有出网调用列全 | 边界外的每一个依赖写清：谁在调、失败了怎么办 |
| 4 | 解决方案策略 | 一页纸讲清为什么是这个分解方式、这个技术选型 | **控制在一页**。写不下说明分解方式本身没想清楚 |
| 5 | 构建块视图 | 系统分解成块，每块一个条目（模板见第五节） | 每个块必须对应一个目录和一个分支。分解只到「一个 Agent 能独立开工」那一级为止，不再往下 |
| 6 | 运行时视图 | 关键场景各走一遍完整链路 | 至少三个场景。只写跨越两个以上构建块的链路，单块内部的流程不写 |
| 7 | 跨领域概念 | 横切多个块的东西：错误格式、日志、配置、鉴权、并发、事件总线 | **只挑最需要的**，不要凑数。判据同第一节的准入测试 |
| 8 | 架构决策 | AD 列表，写法见第三节 | 每条 AD 必须能追溯到至少一个构建块或跨领域概念 |

「已推迟」不单独成节，挂在第八节末尾。

跨模块接口不单独成文档，写在第五节每个块的条目里（见第五节模板的「对外接口」栏）。理由是接口天然属于暴露它的那个块，单开一份接口文档会和块的描述漂移。如果 `CONTRACTS.md` 已经写得很细，保留文件，但每个块的条目要写清它对应 `CONTRACTS.md` 的哪一段。

## 三、架构决策（AD）的写法

一条决策一个编号块，格式固定：

```
### AD-7 — 桌面端只维护一条 SSE

- 约束范围：前端、后端编排
- 防止的分歧：两个渲染进程各自建连接，重连时状态不一致
- 规则：主窗口是唯一的 SSE 消费者；桌宠窗口的所有流式数据经主进程 IPC 转发
- 状态：已采纳
```

四条规矩：

**编号稳定、递增、永不重编号。** 删掉一条决策就留个空号写「已废弃，被 AD-12 取代」，绝不把后面的号往前挪。理由是任务书和代码注释会引用编号。

**三段缺一不可。** 只写「规则」不写「防止的分歧」，读的人不知道边界在哪，遇到规则没覆盖的情况就自由发挥了。

**写决策，不写理由。** 「因为 LanceDB 的向量检索比 SQLite 快」不进 AD，进 commit message 或单独的决策日志。AD 是给执行者看的约束，理由是给未来推翻这条决策的人看的，两拨人不同时读。

**不许写「同 AD-3」。** 每条自包含，重复就重复。

## 四、契约与快照要分开标

文档里的内容分两类，混在一起是架构文档必然过期的根因：

**契约**——长期不变的约束。边界规则、依赖方向、谁拥有哪份数据、状态怎么变更。代码必须服从文档。

**快照**——冷启动时为真的结构。技术栈版本、目录树、数据表字段、接口签名。**代码一旦存在，以代码为准**，文档不再是真相来源。

每个快照性质的表格上方加一行标注：

> 快照：写于 {日期}，代码存在后以代码为准。

这一条决定了维护成本。不标注的话，半年后没人知道文档里哪些还算数。

## 五、构建块条目模板

第五节里每个块用同一个模板，一栏都不能省（没有就写「无」）：

```
### {块名}

- 目录：{相对路径}
- 分支：{分支名}
- 职责：{一句话。超过一句说明这个块该拆}
- 对外接口：{方法签名或事件名。调用方是谁一并写清}
- 依赖：{依赖哪些块。不许出现环}
- 受哪些 AD 约束：{AD 编号列表}
- 未解决的问题：{开工前必须定的，和可以边做边定的，分开列}
```

「依赖」那栏配一张依赖方向图，用 mermaid 画，画谁可以依赖谁。这张图本身就是一条规则，不是配图——依赖方向是并行开发里最容易出分歧的地方。

## 六、Agent 任务书要补两栏

现有任务书的字段（负责什么、目录、先读什么、功能清单、约束、验收标准、与其他分支的接口）保留，补两栏：

**受哪些 AD 约束。** 直接列编号。Agent 开工前必须逐条确认自己理解了每条 AD 的「防止的分歧」那一段。

**未解决的问题，分两档。** 一档是「开工前必须由主调度定的」，另一档是「可以边做边定、定完回报的」。现在这两档混在一起，Agent 分不清哪些能自己拍板，结果要么全问要么全自己决定。

---

## 七、明确不做的事

**不写部署视图。** 单机桌面应用，打包方式属于工程规范不属于架构。

**不写术语表。** 单人项目，术语在上下文里就够。参与人数超过三个再建。

**不建风险登记册。** 现在写出来的风险都是猜的。第一个里程碑跑完之后，用真实踩到的坑建。

**不给每条决策写理由。** 见第三节。

**不追求覆盖率。** 第七节跨领域概念只挑最需要的。一份能读完的短文档，价值高于一份完整但没人读的长文档。
