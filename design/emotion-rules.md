# 丘丘 · 情绪推断规则

`character` 分支的输入，直接翻译成 `packages/character/emotion.ts`。对应 `docs/CONTRACTS.md` § 6 末段。契约版本 **v0.1.2**。

输入是**助手回复的全文**，输出是一个 `10–21` 区间的 `emotionId`，或默认回退 `02`。

## 1 · emotionId 分组的含义

**已联网核对**（2026-09-05，`github.com/sam70361/aora-bot` 的 `README.md` 与 `emotion-ball/js/emotions.js`）。下面不是假设，是上游配置里的原文名称与描述。

分段规则来自上游 README：十位数字即分组前缀，`00–09` 生命周期、`10–29` 情绪反应、`30–49` 代理工作状态、`50+` 自定义；组间空号为新表情预留，**已有编号永不重排**，对接方可以放心硬编码。

实际实现了 32 个：`00–07`（8 个）、`10–21`（12 个）、`30–41`（12 个）。

### `10–21` 情绪反应区间

情绪推断只能落进这 12 个里。

| id | 名称 | 上游描述 | 丘丘用它表达 |
|---|---|---|---|
| `10` | 开心 | 微笑眼环旋转，目光上下点动，身体轻弹跳 | 正向基调：赞同、有兴趣、气氛轻松 |
| `11` | 疑惑 | 质疑眼环，歪头，一眼放大一眼缩小 | **对用户提问**：反问、请求澄清 |
| `12` | 失落 | 困倦眼环慢转，眼睛下沉、目光低垂 | 道歉、办不到、结果不理想 |
| `13` | 惊讶 | 眼睛瞬间放大到 1.45 倍再稳住，身体上提定格 | 意外、出乎预料 |
| `14` | 害羞 | 目光偏向一侧，脸在一秒内慢慢变粉 | 被夸奖、不好意思领功 |
| `15` | 疲惫 | 眼皮半开配困倦眼环，目光低沉 | **不用**（丘丘不表达疲惫，容易被读成服务降级） |
| `16` | 专注 | 专注眼环旋转，双眼微内聚，身体几乎不动 | **不用**（与状态 `30` 思考中重复） |
| `17` | 慌张 | 大眼环高频旋转，目光乱窜，全身发抖 | **不用**（会放大用户的焦虑） |
| `18` | 无奈 | 斜视眼环，歪头，双眼向上翻 | 客观受限、只能这样、摊手 |
| `19` | 满意 | 目视前方，眼睛上下点头式认可 | 事情办妥、确认完成 |
| `20` | 困惑 | 双眼大小不一、斜视，两道目光始终对不上 | **丘丘自己没搞懂**：信息矛盾、理解不了 |
| `21` | 生气 | 瞪眼，脸在 0.25 秒内涨红并保持，身体发抖 | 强烈不认同（对事不对人） |

`11` 与 `20` 的分工是这套规则里最容易搞混的一处，记法：**`11` 问出去，`20` 卡在自己这儿。**

### `30–40` 代理工作状态区间

功能表情，**不参与情绪推断**，只由状态机与记忆事件驱动（见 `design/state-machine.md` § 1、§ 3）。

| id | 名称 | 上游描述 | 丘丘用在哪 |
|---|---|---|---|
| `30` | 思考中 | 思考眼环旋转，目光向上巡视，头顶环带 | 状态 `thinking` |
| `31` | 接收任务 | 快速眨眼并轻微放大，像点头确认 | 不用 |
| `32` | 处理中忙碌 | 专注眼环旋转，目光小幅绕圈 | 不用 |
| `33` | 任务完成 | 微笑眼环，庆祝甩彩带并撒花 | 不用（`19` 满意已够，撒花在桌宠上过头） |
| `34` | 出错 | 大眼环，脸红白闪烁后停在警示红 | 事件：请求出错 |
| `35` | 等待输入 | 倾听眼环旋转，目光上下轻扫 | 状态 `listening` |
| `36` | 联网加载 | 双眼交替眨动，像信号在两端跳 | 不用 |
| `37` | 复述回忆 | 倾听眼环慢转，目光上飘，像在翻记忆 | 事件：`recall` 命中 |
| `38` | 拒绝/受限 | 目光下垂斜视，切入时坚定摇头 | 事件：回复含拒绝 |
| `39` | 输出回复 | 阅读眼环旋转，带与输出同步的轻脉动 | 状态 `speaking` |
| `40` | 检索资料 | 六组阅读眼环高速旋转，目光快速左右扫 | 事件：`recall` 下探冷存储 |

（`41` 停止终止在 `30–41` 区间内但不在任务书要求的 `30–40` 范围，丘丘不用。）

## 2 · 何时跑、跑在什么文本上

- **只在 SSE `done` 事件之后跑一次**，对本轮回复全文。绝不在 `delta` 途中跑——半句话的正则命中率高得离谱，而且会让丘丘在一轮里变四次脸。
- 结果作为一条**事件表情**送进 `design/state-machine.md` § 3 的通道，优先级 `30`，持续 1600 ms，之后回到当前状态的表情。
- 优先级 `30` 低于全部记忆事件。同一轮里既有 `write` 事件又推断出情绪时，`write` 的 `10` 开心胜出——记忆可见性是排序第一的质量属性。

### 预处理

```ts
function normalize(raw: string): string {
  return raw
    .replace(/```[\s\S]*?```/g, ' ')        // 围栏代码块
    .replace(/`[^`\n]*`/g, ' ')             // 行内代码
    .replace(/!?\[[^\]]*\]\([^)]*\)/g, ' ') // markdown 图片与链接
    .replace(/https?:\/\/\S+/g, ' ')        // 裸 URL
    .replace(/\s+/g, ' ')
    .trim();
}
```

去代码与 URL 是必需的：代码注释里的 `// TODO: 这里有问题` 会误触发 `20` 困惑。

### 三个作用域

| 作用域 | 定义 |
|---|---|
| `全文` | `normalize(raw)` |
| `末80` | `全文.slice(-80)` |
| `末句` | 用 `全文.split(/(?<=[。！？!?…；;])(?![。！？!?…；;])/)` 切分，取最后一个非空段；切不出来时等于 `全文` |

`末句` 存在的理由：中文回复的情绪落点几乎总在最后一句。「这里有三种做法。你想先试哪一种？」——全文是陈述，末句是提问，情绪应当判成 `11` 疑惑。

切分正则里的后行否定 `(?![。！？!?…；;])` 不能省。省掉的话「这条记录还在！！」会被切成 `["这条记录还在！", "！"]`，末句只剩一个感叹号，R04 的 `{2,}` 判不到，结果掉进 R17 变成 `10` 开心。连续标点必须留在同一段里。

## 3 · 规则表

按 `优先级` 从大到小逐条 `regex.test(scope)`，**第一条命中即返回**，不累计打分。全部不命中返回默认 `02`。

所有正则带 `u` 标志。

### 覆盖检查

任务书要求的九种情绪，逐一对应：开心 `10` / 疑惑 `11` / 失落 `12` / 惊讶 `13` / 害羞 `14` / 无奈 `18` / 满意 `19` / 困惑 `20` / 生气 `21`。默认回退 `02`。

### 优先级为什么这么排

从上往下是「越少见、越强烈的越先判」。`10` 开心排最后是因为 R16 的词表最宽，放前面会把「抱歉，不错的思路，但是……」判成开心。反过来，「太好了，我已经记下了！」会先命中 R14（`19` 满意，P40）而不是 R16（`10` 开心，P30）——办妥事的语气优先于泛泛的高兴，这是刻意的。

同优先级内按表里的行序判（R01 先于 R02，R03 先于 R04，以此类推）。

### 三个容易判错的组合，用例写进单测

| 输入 | 期望 | 为什么 |
|---|---|---|
| 「不好意思，我没查到那条记录。」 | `12` 失落 | R05 的害羞词表里**没有**孤立的「不好意思」；R06 用 `不好意思[，,]` 精确匹配道歉用法 |
| 「你这么夸我，我有点不好意思。」 | `14` 害羞 | 命中 R05 的 `夸得我`？不命中。命中 `(?:你\|您)(?:太)?过奖`？不命中。**这条会落到 `02`** —— 已知缺口，见下 |
| 「这两条对不上，你是说哪一条？」 | `11` 疑惑（P50） | R11 末句问号先于 R13 的 `对不上`（P45） |

第二行是已知的欠命中：`不好意思` 归给了道歉。补法是给 R05 加 `/(?:你\|您)这么夸/u`，已并入上表的 R05。若单测仍有缺口，`character` 可以往 R05 的词表里加词，**但不许改优先级**——优先级顺序是本文的契约面。

## 4 · 拒绝式（供 `38` 拒绝/受限 使用）

这条不属于 `10–21` 情绪推断，但同样在 `done` 之后对全文跑，结果送进事件表情通道，优先级 `80`（见 `design/state-machine.md` § 3）。命中时用 `38`，且**跳过** § 3 的情绪推断。

```ts
const REFUSAL = /(我(?:不能|无法|没法)(?:帮你)?(?:提供|回答|完成|做|参与)|超出(?:我的)?(?:能力|权限|范围)|(?:这|该)(?:类|个)(?:问题|请求)我(?:不便|不能)|建议(?:你)?(?:咨询|寻求)(?:专业|医生|律师|心理)|我不是(?:医生|律师|心理咨询师)|不适合由我来(?:判断|决定)|我们的关系(?:是|只是))/u;
```

作用域 `全文`。最后两条对应 `docs/ARCHITECTURE.md` § 4 的人格安全边界——不模拟恋爱关系、不诱导依赖、不替代医疗法律心理建议。

## 5 · 参考实现形状

`character` 照这个结构写，`RULES` 数组的内容与顺序必须与 § 3 的表逐行一致。

```ts
export type Scope = 'full' | 'tail80' | 'lastSentence';

export interface EmotionRule {
  id: string;            // 'R01' … 'R17'
  priority: number;
  scope: Scope;
  pattern: RegExp;
  emotionId: string;     // 只能是 '10'|'11'|'12'|'13'|'14'|'18'|'19'|'20'|'21'
}

export const FALLBACK_EMOTION = '02';

export function inferEmotion(raw: string): string {
  const full = normalize(raw);
  if (!full) return FALLBACK_EMOTION;
  const scopes: Record<Scope, string> = {
    full,
    tail80: full.slice(-80),
    lastSentence: lastSentenceOf(full)
  };
  for (const rule of RULES) {            // RULES 已按 priority 降序、同级按 id 升序排好
    if (rule.pattern.test(scopes[rule.scope])) return rule.emotionId;
  }
  return FALLBACK_EMOTION;
}
```

```ts
export const REFUSAL = /(我(?:不能|无法|没法)(?:帮你)?(?:提供|回答|完成|做|参与)|超出(?:我的)?(?:能力|权限|范围)|(?:这|该)(?:类|个)(?:问题|请求)我(?:不便|不能)|建议(?:你)?(?:咨询|寻求)(?:专业|医生|律师|心理)|我不是(?:医生|律师|心理咨询师)|不适合由我来(?:判断|决定)|我们的关系(?:是|只是))/u;

function lastSentenceOf(full: string): string {
  const parts = full.split(/(?<=[。！？!?…；;])(?![。！？!?…；;])/).filter(s => s.trim());
  return parts.length ? parts[parts.length - 1] : full;
}
```

三条硬要求：

1. `RULES` 里的 `pattern` **不带 `g` 标志**。带 `g` 的正则 `test()` 有 `lastIndex` 副作用，连续两次调用结果不同。
2. `inferEmotion` 必须是纯函数，同样的输入永远同样的输出，方便 `packages/character` 的契约测试。
3. 返回值必须落在本文列出的 10 个 ID（9 个情绪 + 回退 `02`）之内。返回任何其它 ID 视为实现错误。
